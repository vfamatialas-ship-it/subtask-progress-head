# 子任务自动切换

四段串跑里,每个专家内部的子任务推进从「人按空格」换成「进度头自动判断」。
专家**之间**的切换仍由 `run_chain_4stage.py` 的确定性顺序调度 —— 不用分类器。

```bash
python3 run_chain_4stage.py --host <POLICY_SERVER_IP> --execute --auto-advance --auto-switch
```

空格随时可以手动覆盖:人按了键就按人的来,那一步不合成。

---

## 它是什么

一个**子任务进度头**:三路相机 → SigLIP2-so400m 视觉塔 → 小 MLP,输出
`(progress, done, time-to-boundary)`,取 `min` 当信号。信号超过按 (专家,子任务)
标定的 τ、连续 K=8 帧,再等 D 步延迟补偿,就切下一个子任务。

四道防抖:

| 机制 | 作用 |
|---|---|
| **只吃当前帧** | 不喂帧号、不用时序模型。卡顿时输入不变 → 输出不变 → 进度天然不推进 |
| **停滞门控** | `Δstate < 1e-5` 算没动就冻结计数。**但只在信号未过线时冻结** —— 已过线的静止是「做完了停那儿」,该切就切 |
| **迟滞 lockout=10** | 切换后 10 步内不许再切 |
| **max_steps 兜底** | 超步数还没触发就强制推进,不会永远卡住 |

## 为什么专家之间不用模型

试过三分类图像分类器:逐帧准确率 100%,但时序剖面完全平坦(E1 的集跑到 90%
进度时,预测 E3 仍是 0%)。它学的是「这帧来自哪个数据集」,不是「该切了」——
四个数据集分别录制,决策边界根本不在数据里。

所以专家调度用确定性计数器 + 进度头的 `finished`。这正好和 chain 现有的编排方式
吻合:chain 本来就是按顺序调起四个客户端。

## ⚠ 两条最容易翻车的

### 1. `step()` 必须跟相机帧走(15Hz),不能跟推理走

τ / 延迟 D / 连续 K 帧 / EMA **全是步数量纲**的,按数据集 15fps 标定。
调用频率一降,同样步数覆盖的视觉距离就成倍放大。原作者实测:

| 调用频率 | 整集跑完 | 落在 ≤8% 段长内 |
|---|---|---|
| **15 Hz(正确)** | **73/73** | **76%** |
| 10 Hz(1.5×) | 73/73 | 62% |
| 5 Hz(3×) | **64/73** | **4%** |

所以钩子挂在客户端内层 `for i in range(n_exec)` 循环里(那层每帧读一次相机、
末尾 `sleep(PERIOD)`),**不是**挂在每次策略推理旁边。
`--execute-horizon 50` 时推理只占约 4% 时间,有效帧率 ≈14.4Hz。

### 2. 停滞阈值要在真机相机上重标

`stall_img_eps=0.032` 是在**压缩视频**上标的 —— H.264 把静止区域量化成完全相同的块,
噪声被抹掉了。真机实时相机的传感器噪声就能让静止画面的逐像素差超过 1,
用这个阈值**永远不会触发**。

所以图像通道**默认关闭**,只用 `Δstate`(网络卡顿时机械臂停住、编码器读数恒定,
这才是真机上可靠的信号)。要启用图像通道先标定:

```python
from switcher import calibrate_stall
eps_img, eps_st = calibrate_stall(still_imgs, still_states, moving_imgs, moving_states)
```

两个分布重叠时它会告警 —— 那说明该通道在你的硬件上区分不了停滞,别用。

## 架构:为什么拆成两个进程

rollout 客户端跑**系统 python3**(lerobot / cv2 / pyrealsense2),切换器要
**torch cu128 + transformers**。而本机系统 torch 是 `2.13.0+cpu` —— 换掉它会连累
lerobot 的视频编码。所以:

```
系统 python3                        独立 venv (switcher_pkg/.venv)
┌──────────────────────┐            ┌────────────────────────────┐
│ run_pi05_rollout_*   │  Unix      │ switcher_service.py        │
│   └ switcher_client  │◄─socket───►│   └ switcher.py            │
│      resize 到 224    │            │      SigLIP2 + 进度头       │
└──────────────────────┘            └────────────────────────────┘
```

图像在**客户端**就缩到 224×224 再发:450KB/步 @15Hz = 6.8MB/s,比发原图
(2.7MB/步)省 6 倍;切换器内部本来也要缩到 224,总计算量不变。

服务进程由客户端自动拉起,**四段接力共用一个** —— 省下每段重新加载 816M 视觉塔的
几秒。chain 在整条链结束时统一停掉(`--keep-switcher` 可保留)。

### 必须用 GPU

实测 SigLIP2-so400m 三张图前向:

| 设备 | 单步 | 上限 |
|---|---|---|
| CPU(Xeon 6426Y 64核) | 363 ms | 2.8 Hz |
| **需要** | **< 66.7 ms** | **15 Hz** |

CPU 差 5.4 倍,而 5Hz 就崩到 4% —— **CPU 方案不可行**。

本机是 RTX 5060 Laptop(sm_120 Blackwell),要 cu128 的 torch:

```bash
python3 -m venv deploy/switcher_pkg/.venv          # 不加 --system-site-packages
deploy/switcher_pkg/.venv/bin/pip install --index-url https://download.pytorch.org/whl/cu128 torch
deploy/switcher_pkg/.venv/bin/pip install transformers numpy pillow
```

> 服务器 <SERVER> 的 torch 2.7.1+cu126 只支持到 sm_90,**跑不了它自己的
> 5090 / PRO5000**。要在服务器上跑切换器同样得先装 cu128。

## 模型来自哪

`switcher_pkg/progress_head.pt` = `runs/p_third_right_left_e0123_eeall_s2/best.pt`。

**为什么是这个而不是原部署包那个**:原包的 expert 1(左臂)是 **16 维关节角**,
而 chain 里的 E1 用的是末端位姿版模型(10 维 EE)。`eeall` 系列是按全 EE 重训的,
`state_dim = {0:10, 1:10, 2:20, 3:20}`。

三个种子在留出集上串行回放(误差会累积,最贴近真机):

| run | 跑完整集 | ≤10帧 | ≤20帧 | 兜底 |
|---|---|---|---|---|
| `eeall` | 69/73 (95%) | 75% | 89% | 5 |
| `eeall_s1` | 70/73 (96%) | 72% | 88% | 9 |
| **`eeall_s2`(选它)** | **70/73 (96%)** | **76%** | **91%** | **5** |

逐专家:

| 专家 | 跑完整集 | 切换数 | 误差中位 | ≤10帧 | ≤20帧 |
|---|---|---|---|---|---|
| E0 右臂抓盒 | 16/18 | 34 | −4 | 65% | 91% |
| E1 左臂抓盒 | 16/16 | 32 | +0 | 75% | 84% |
| E2 stage34 | 24/25 | 174 | −1 | 74% | 92% |
| E3 stage56 | 14/14 | 98 | +0 | 85% | 90% |

76%/91% 与原部署版发布的指标持平。

> 原部署那份 16 维权重现在**已经无法评估** —— 特征缓存 8/26 就重建成 10 维了,
> 加载直接报 `expanded size (16) must match existing size (10)`。

## 客户端侧怎么接的

钩子只做一件事:**切换器说该切了,就把 `key` 置成 `" "`**。

```python
key = (keypad.get(0.0) or "").lower()
if sw is not None:
    _r = sw.step(frames, state)          # 每帧都调, 不管有没有按键
    if _r["switched"] and not key:       # 人按了键就按人的来
        key = " "                        # ← 后面所有既有分支原样跑
```

为什么不直接写推进逻辑:单臂客户端(rightbox/leftbox)在空格分支里内联做
`seg_bounds` / `sid += 1` / `label = "s"`;双臂客户端(hezi/stage56)是
`advance = "next"` 再交外层处理。两套簿记不一样,各写一遍等于把两份已验证的逻辑
复制成四份没验证的。合成按键则一行都不用改。

`switched` 在切下一段和整个专家做完时**都为真**(见 `switcher.py:step`),
所以最后一段完成会像人按空格一样让本阶段正常收尾,chain 接力到下一段。

出错时自动退回手动:`sw.step()` 抛异常就打印一行并把 `sw` 置 None,后面全靠空格。

1. `--dry-run` 验编排

3. 标定停滞阈值(见上面第 2 条)
4. 再开 `--execute`
