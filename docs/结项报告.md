## ⚠ 上机前必读：`sw.step()` 必须按 15 Hz 调用

数据集是 **15 fps**，τ / 延迟 D / 连续 K 帧 / EMA 全部按这个帧率标定 ——
它们都是**步数量纲**的量。**不要**写成「每步策略推理调一次」：
策略只跑 5~10 Hz，那等于 1.5~3 倍快放。

| 调用频率 | 整集跑完 | 视觉位置误差 | 落在 ≤8% 段长内 |
|---|---|---|---|
| **15 Hz（正确）** | **73/73** | **+0.0%** | **76%** |
| 10 Hz（1.5×） | 73/73 | +5.3% | 62% |
| 7.5 Hz（2×） | 72/73 | +11.1% | 32% |
| **5 Hz（3×）** | **64/73** | **+23.6%** | **4%** |

按 5 Hz 调用，准确率从 76% 崩到 **4%**，还有 9/73 集跑不完。

`sw.step()` 单步只要 7 ms，按 15 Hz 只占 10% 占空比。正确写法是让它跟着
**相机帧**走，策略照常按自己的频率跑、每次读当前 prompt：

```python
prompt = None
while True:
    frame = camera.latest()                  # 15 Hz
    r = sw.step(frame.images, frame.state)
    prompt = r["prompt"]
    if r["finished"]:
        break
    if policy.ready():                       # 5~10 Hz，各跑各的
        robot.exec(policy.infer(frame, prompt=prompt))
```

相机若不是 15 fps，先降采样到 15 Hz 再喂给 `sw.step()`。

> **顺带更正**：本文档早前把容差按 30 fps 换算成秒（「20 帧 = 0.67 秒」）是错的。
> 实际数据集是 15 fps，**20 帧 = 1.33 秒**，容差的真实时长是先前所说的两倍。

## 用法

```python
from switcher import SubtaskSwitcher

sw = SubtaskSwitcher(expert=2)          # 0=E1右臂 1=E2左臂 2=E3封箱
while True:
    obs = robot.get_obs()
    r = sw.step({"third_view":  obs.third_rgb,      # HxWx3 uint8 RGB
                 "right_wrist": obs.right_rgb,
                 "left_wrist":  obs.left_rgb},
                obs.state)                           # 1-D float 关节/末端
    action = policy.infer(obs, prompt=r["prompt"])   # ← 用返回的 prompt
    robot.exec(action)
    if r["finished"]:                                # 该专家全部子任务完成
        break
```

`r` 还含 `progress / signal / ema / tau / hits / pending / switched / stalled /
frozen / forced`，打日志就能看出它为什么切、为什么不切。

**专家级调度用确定性计数器，不用模型**（理由见下文）：

```python
for cycle in range(6):                          # 6 个盒子
    run_expert(0 if cycle % 2 == 0 else 1)      # E1/E2 交替，各自跑到 finished
run_expert(2)                                   # 装满 → 封箱
```

## 关键数字

全部在**留出集**上测；τ / 延迟 / 兜底步数全部在**训练集**上标定。

| 项目 | 结果 |
|---|---|
| 串行回放 跑完整集 | **59/60** |
| 切换时刻 \|误差\|≤10 帧 | **76~77%** |
| 切换时刻误差 ≤20 帧 | **90%**（15 fps 下 = 1.33 秒） |
| 误差中位 | −2 帧 |
| 兜底强制推进 | 3 次 / 209 次切换 |
| 专家级握手（末子任务）检出 | **60/60**，97% 在 ±20 帧内 |
| 单步延迟 | **6.8~7.1 ms**（约 140 Hz） |

串行回放 = 整集跑状态机，第 n 段的起点是上一段**实际**切走的位置，误差会累积。
这比分段评估严格，也是真机的行为 —— 所有定稿决策都按这个口径做。

### 抗卡顿：两道保险都验证过

| 测试 | 结果 |
|---|---|
| 静止 30 帧的进度漂移 | 中位 **0.0000** / 最大 **0.0000** |
| 注入 90 步卡顿（走真实部署代码） | 门控冻结 90/90 步，切换时刻偏移中位 **0 帧**、最大 0 帧 |
| 同上但门控失效时 | 仍全部跑完、偏移中位 0 帧，但最坏出现 **45 帧**偏移 |
| 门控开 / 关的整体差异 | 76% vs 77%（门控冻结了 10.4% 的帧，几乎无影响） |

**扛住卡顿的主力是「模型只吃当前帧」这个设计本身**，门控是第二道保险 ——
它把最坏情况从 45 帧压到 0 帧。

### 重试误报：曾标为「无法验证」，现已验证通过

数据集全是成功演示，所以「抓空后退回重来会不会让模型误以为快做完了」一直没法验。
构造方法：在段内 80% 处插入 40 帧「退回到 30% 位置」的画面，再接回原序列。

- 倒带期间进度**回落**的段占 **94%** → 模型在读世界状态，重试骗不到它
- 倒带段内误触发 **0/126 = 0%**
- 扣除插入帧后净触发偏移中位 **0 帧**，94% 在 ±5 帧内 → 倒带过后判断完全恢复

### 扰动鲁棒性

| 情形 | 跑完整集 | ≤10帧 | ≤20帧 |
|---|---|---|---|

## ⚠ 上机前必做：标定停滞阈值

停滞门控默认只用 `Δstate`（`stall_state_eps=1e-5`），**图像通道默认关闭**。

包里的 `stall_img_eps = 0.032` 是在**压缩视频**上标出来的。H.264 把静止区域量化成
完全相同的块，噪声被抹掉了；真机实时相机的传感器噪声就能让静止画面的逐像素差
超过 1 —— **门控在真机上会永远不触发**。反过来，网络卡顿时机械臂停住、
编码器读数恒定，`Δstate` 才是真机上可靠的指标。

要启用图像通道，先用包里的 `calibrate_stall()` 在你的相机上标：
采一段机械臂静止（断开控制让它停住）、一段正常运动，函数会给出阈值；
两个分布重叠时会直接告警 —— 那说明该通道在你的硬件上区分不了停滞，别用。

## 三个结论性的负结果

### 一、专家级切换用图像分类器：不可行

训了 E1/E2/E3 三分类。**逐帧准确率 epoch 0 就 100%、混淆矩阵全对角**，
但**时序剖面完全平坦** —— E1 集直到 90% 进度，预测为 E3 的概率仍是 **0%**；
E3 集从**第 0 帧**起就是 **100%**。

这是**捷径学习**：它学的是「这帧来自哪个数据集」（录制时段、光照、机位、
机械臂初始构型），不是「现在该切换了」。部署后果很明确 —— E1 放完一个盒子后
画面仍是 E1 场景，分类器永远说 E1，**握手永远不会触发**。

**根因：决策边界不在数据里**。三个数据集分别录制，没有任何一集横跨
「箱子没满 → 装满 → 开始封箱」这个转变。

**替代方案（已验证）**：确定性计数器 + 进度头的 `finished`
（60/60 全部检出，97% 在 ±20 帧内）。一行分类器都不需要。

若仍要做分类器，缺的是**数据**不是模型：要么录横跨转变的连续集
（同一机位同一光照，从空箱装到满箱再封箱），要么在第三视角上标「箱内盒子数」
（几百帧即可，这是个慢变量）。拿现有三个数据集重训多少次都不会有用。

### 二、线性 vs event_code 分段 progress：这个对照做不了

每段恰好 **1 个**事件锚点，且全部落在 `p_t = 1.000` —— 锚点与 `prompt_index`
游程边界完全重合，不含任何额外信息。没有可分的子相位，
线性进度已经是这套标签能给出的全部。

### 三、精度优化：三条路都在噪声带内，76% 是天花板

先确立标尺：**只换随机种子，`≤10帧` 就在 72%~77% 之间摆动**。
所以在这个留出集上**小于约 5 个点的差异都是噪声**，
任何改动都必须 **3 个种子比均值**，不能看单次结果。

基线（全局向量 + aug1）：72 / 77 / 76 → **均值 75.0**，跑完 59/59/59。

| 尝试 | 三种子 ≤10帧 | 均值 | 跑完整集 | 结论 |
|---|---|---|---|---|
| **基线（定稿）** | 72 / 77 / 76 | **75.0** | 59/59/59 | — |
| 多头集成 ×3 | — | 74 | 59/60 | 无提升 |
| 加第二份几何增强 | 76 / 77 / 74 | 75.7 | 57/58/59 | 无提升 |
| 网格池化 2×2 特征 | 69 / 78 / 76 | 74.3 | 57/56/57 | 无提升 |

三条路动机不同，结果一致：

1. **多头集成** —— 赌误差是方差型的。结果集成只等于三个单头的平均，
   没超过最好的那个；大概是平均化让信号变平滑，削弱了判据依赖的
   「连续 K 帧过线」那个锐度。
2. **第二份几何增强** —— 赌数据多样性不够。差 0.7 点，跑完率还略差。
3. **网格池化特征** —— 赌 `pooler_output` 的全局池化抹掉了
   「盒子在不在夹爪里」这类**空间局部**信息。**这个假设被证伪了**：
   改成保留 2×2 空间网格（每视角 4×1152）之后并没有变好。

**这说明**残余误差不是「特征不够好」或「容量不够」，而是**单帧进度估计的固有歧义** ——
同一段动作在 45% 和 55% 处，画面和 state 都几乎一样。能真正打破这个歧义的手段
（**时序上下文**）正是设计约束明确排除的：喂帧号/时长/时序模型会在卡顿时继续漂移，
而那正是这套方案要解决的首要问题。

所以 **76% 是「只吃当前帧」这套方法在这份数据上的天花板**。
再提升需要质变（更多数据），而放宽抗卡顿约束不划算 ——
`≤20帧` 已有 90%，15 fps 下即 1.33 秒，对切 prompt 完全够用。

## 两个对照实验的结论

### 视角：推翻了「只用第三视角」的原定方案

原理由是「腕部随手臂动 = 时间性线索，与抗卡顿冲突」。**数据不支持**：

| 视角 | 跑完整集 | ≤10帧 | ≤20帧 |
|---|---|---|---|
| **三视角（采用）** | **60/60** | **78%** | 90% |
| 仅腕部 | 55/60 | 74% | 86% |
| 仅第三视角 | 54/60 | 67% | 82% |

`observation.state`（关节/末端位姿）**本来就是所有版本的输入**，
所以「腕部编码手臂位姿 ⇒ 轨迹相位」这条论证不成立 —— 相位信息第三视角版早就有。
仅腕部版比仅第三视角版好 7 个点，多出来的只能是**夹爪附近的细粒度世界状态**
（东西抓住没有、盖子贴合没有），这些从远处固定机位看只有几个像素。

三个版本的卡顿漂移都是 0.0000，抗卡顿并不能区分它们；
而倒带测试进一步证明三视角版读的确实是世界状态（94% 回落、0% 误触发）。

### 标签：零人工

数据集里 `prompt_index` 是逐帧记录的，同一子任务是一段连续游程，
游程起止即子任务边界。导出 188,873 帧 / 1300 段 / 400 集，**顺序异常 0 集**，
事件锚点数与段数完全对齐。不需要任何人工标注。

## 设计要点

- **只吃当前帧**：不喂帧号、不喂已执行时长、不用时序模型。
  卡顿时输入不变 → 输出不变 → 进度不推进。
- **停滞门控只在信号未过线时冻结**：要防的是「卡顿期间 EMA 慢慢爬过阈值」这种
  假阳性；信号已过线的静止说明「做完了停在那儿」，该切就切。
- **EMA 平滑是安全的**：卡顿时输入恒定，EMA 收敛到该常数后不再变化。
- **延迟补偿 D 按推理步计**，不按墙钟时间，且同样受门控冻结。
- **ttb 头**：线性 p 把容量摊在整段上，但决策只发生在段末几十帧 ——
  段中 40% 和 60% 分不清对切换毫无影响，却占了大部分 loss。
- **操作点按串行口径选**：分段口径让每段从真边界起算，掩盖误差累积，
  会挑出不同（更差）的信号。

## 踩过的坑

**数据与环境**

1. **cv2 静默解不了 AV1**：两路腕部相机是 AV1，cv2 返回失败但不报错，
   特征全成零 → 模型等于只看第三视角。改 PyAV(libdav1d)，
   零特征比例 `[0,100%,100%]` → `[0,0,0]`。
2. **Blackwell 不兼容**：GPU2/3 是 RTX PRO 5000（sm_120），openpi_venv 的
   torch 2.7.1+cu126 报 `no kernel image is available`。必须用
   `<WORK_ROOT>/sam2pp/venv/bin/python`（torch 2.13+cu130）。
3. **`task_index` 不是执行顺序**：E3 的执行序是 task_index `[0,6,5,2,1,4,3]`。
   部署必须按 `prompt_index` 走，直接拿 tasks.jsonl 的顺序会全错。
4. **网格特征 4 倍大导致 OOM**：整块塞显存会和占卡进程撞车。
   已改为特征常驻 CPU、按批送 GPU —— 本来就该这么写。

**评估口径（这一类最容易得出错误结论）**

5. **逐帧 MAE 会骗人**：MAE 0.083 看着不错，但按 p>0.85 连续 5 帧的规则漏切 45.8%。
   回归把两端往均值压，段末冲不到阈值。
6. **按「漏切率最低」选操作点是错的**：会退化到 τ→0 —— 从不漏切，
   但提前 86 帧触发。必须用「触发了 **且** 时机对」的单一指标。
7. **标定要用 sustained-K 而不是峰值**：触发规则要求连续 K 帧过线，
   瞬时峰值 0.97 只闪一帧的段，用峰值标定出的 τ 根本触发不了。
   这一条占了早期 41% 漏切的绝大部分。
8. **评估集混进训练集**：第一版在全部 100 集上评，指标虚高。
   现在 val episode 存进 ckpt，评估只在留出集上做。
9. **联合版 τ 分组错误**：把 E1 的 sub1 和 E3 的 sub1 混成一档。
   改按 (专家,子任务) 分组，漏切 13.8% → 11.4%。
10. **串行回放「50% 卡住」是假象**：卡住的全在最后一个子任务 ——
    最后一段的真实边界就是整集最后一帧，触发后还要等 D 步延迟补偿，帧就用完了。
    真机不会在那一刻停止推流。补上末帧保持后是 100%。
11. **停滞门控一步都没冻结**：`Δstate` 的 p1/p5 都是 0（真实运动中 state 常常
    整帧不变），按「p1 的一半」算出的阈值是 **0**，而 `d_st < 0` 恒为假 →
    门控形同虚设。给正下限（1e-5）后冻结 90/90 步。
12. **扰动测试抽样有偏，把结论带偏过两次**：原本取「每个专家排序后的前 4 集」，
    这个子集系统性偏难（≤10帧 **50%**，其余 48 集 **84%**）。据此先后得出过
    「必须带增强重训、不能上机」和「增强版反而变差」两个错误判断。

13. **最早的扰动测法不现实**：三路视角一起扰动 = 假设三个相机同时被碰。

## 部署速度与采集速度不一致：模型没问题，判据有轻微漂移

**问题**：进度标签是按采集时间线性插值的（`p_t = (t−起点)/(终点−起点)`）。
如果模型学到的是「时间」而不是「场景」，部署时机械臂快慢一变就全乱。

**测法**：把整集**重采样**成不同速度再跑状态机。0.5× 是每帧复制（手臂每步走一半距离），
2.0× 是隔帧取。真边界在重采样下标空间里变成 `boundary / speed`。

分两个量看：**视觉位置误差**（触发点偏离真边界多少，占该段长度的百分比）
—— 这个量与速度无关才说明模型读的是场景；**折回原帧误差** —— 受步数量纲的判据影响。

| 速度 | 整集跑完 | 视觉位置误差 | 占段长≤8% | 折回原帧 |
|---|---|---|---|---|
| 0.5× 慢一半 | 59/60 | −7.1% | 53% | −10 帧 |
| 0.75× | 59/60 | −3.8% | 71% | −5 帧 |
| **1.0× 原速** | 59/60 | **−1.0%** | **75%** | −2 帧 |
| 1.5× | 59/60 | +3.8% | 70% | +6 帧 |
| 2.0× 快一倍 | 58/60 | +9.3% | 38% | +14 帧 |

**结论分两半**：

- **模型本身对速度不敏感**（好消息）：跑完率 58~59/60 全程不变，不会因为速度变了
  就卡死或乱切。这印证了它读的是场景不是时间 —— 与静止 30 帧漂移 0.0000、
  倒带 94% 回落这两个结果一致
- **判据有单调随速度的漂移**（要知道）：慢放早切、快放晚切，0.5×/2.0× 时约
  ±7~9% 段长。根因是判据里有三个**步数量纲**的部件：
  延迟补偿 D、连续 K 帧、EMA 平滑 α。慢放时 8 步只覆盖 4 个原始帧的视觉距离，
  等于 debounce 变短 → 视觉上更早触发

### 试过的两种自适应，一个有用一个是倒退

| 配置 | 0.5× | 1.0× | 2.0× |
|---|---|---|---|
| **固定 K/D（现状，定稿）** | −7.1% / 53% | **−1.0% / 75%** | +9.3% / 38%（58/60） |
| 自适应 D（**段末**窗口估速） | −7.4% / 49% | −2.9% / 68% | **+2.9% / 71%** |
| 自适应 K+D（**段首**窗口估速） | −3.4% / 59% | +1.7% / 62% | +13.4% / 28%（**39/60**） |

- **自适应 D 有效**：把快放侧从 +9.3%/38% 压到 +2.9%/71%，代价是原速掉 7 个点
- **再缩放 K 是倒退**：2× 时跑完率从 58/60 崩到 **39/60**。原因是我把估速窗口
  放在段**首**，而那里信号还在 EMA 初始化、并不稳定上升，估出的比值是噪声；
  比值偏大就让 K 和 D 同时膨胀 → 漏切。段**末**窗口才可靠（信号确实在稳定上升）

**定稿仍用固定 K/D**，理由：部署是同一台机器人同一套控制器，速度应当接近采集时；
原速下固定版最好（75% vs 68%）。若实测速度与采集差 1.5 倍以上，
再换自适应 D（`tools/speed_test.py` 里有实现）。
