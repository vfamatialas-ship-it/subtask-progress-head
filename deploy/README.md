> `E1→E0 右臂抓放` · `E2→E1 左臂抓放` · `E3→E2 封箱中段` · `E4→E3 封箱末段`。

## ⚠⚠ 最重要的一条：`sw.step()` 必须按 **15 Hz** 调用

数据集是 **15 fps**，τ / 延迟 D / 连续 K 帧 / EMA 全部按这个帧率标定。
这几个量都是**步数量纲**的 —— 调用频率一降，同样步数覆盖的视觉距离就成倍放大。

**不要**写成「每步策略推理调一次」。策略只跑 5~10 Hz，那等于 1.5~3 倍快放：

| 调用频率 | 整集跑完 | 视觉位置误差 | 落在 ≤8% 段长内 |
|---|---|---|---|
| **15 Hz（正确）** | **73/73** | **+0.0%** | **76%** |
| 10 Hz（1.5×） | 73/73 | +5.3% | 62% |
| 7.5 Hz（2×） | 72/73 | +11.1% | 32% |
| **5 Hz（3×）** | **64/73** | **+23.6%** | **4%** |

按 5 Hz 调用，准确率会从 76% 崩到 **4%**，还有 9/73 集跑不完。

`sw.step()` 单步只要 **7 ms**，按 15 Hz 调用只占 10% 占空比。正确写法是让它
跟着**相机帧**走，策略照常按自己的频率跑、每次读当前 prompt：

```python
prompt = None
while True:
    frame = camera.latest()                  # 15 Hz
    r = sw.step(frame.images, frame.state)
    prompt = r["prompt"]
    if r["finished"]:
        break
    if policy.ready():                       # 5~10 Hz，各跑各的
        robot.exec(policy.infer(frame, prompt=prompt))
```

若相机帧率不是 15，先降采样到 15 Hz 再喂给 `sw.step()`。

## 用法

```python
from switcher import SubtaskSwitcher

sw = SubtaskSwitcher(expert=2)     # 0=E1右臂 1=E2左臂 2=E3封箱中段 3=E4封箱末段
while True:
    obs = robot.get_obs()
    r = sw.step({"third_view":  obs.third_rgb,      # HxWx3 uint8 RGB
                 "right_wrist": obs.right_rgb,
                 "left_wrist":  obs.left_rgb},
                obs.state)                           # 1-D float 关节/末端
    action = policy.infer(obs, prompt=r["prompt"])   # ← 用返回的 prompt
    robot.exec(action)
    if r["finished"]:                                # 该专家全部子任务完成
        break
```

`r` 还含 `progress / signal / ema / tau / hits / pending / switched / stalled /
frozen / forced`，打日志就能看出它为什么切、为什么不切。

## 专家级调度：不用分类器

E1/E2/E3/E4 之间的切换**不需要模型**。试过三分类图像分类器，逐帧准确率 100% 但
时序剖面完全平坦（E1 集到 90% 进度时预测 E3 仍是 0%）—— 它学的是「这帧来自哪个
数据集」，不是「该切了」。数据集分别录制，决策边界不在数据里。

改用确定性计数器 + 进度头的 `finished`：

```python
for cycle in range(6):                          # 6 个盒子
    run_expert(0 if cycle % 2 == 0 else 1)      # E1/E2 交替，各自跑到 finished
run_expert(2)                                   # 装满 → 封箱中段
run_expert(3)                                   # → 封箱末段
```

## ⚠ 上机前必做：标定停滞阈值

停滞门控默认只用 `Δstate`（`stall_state_eps=1e-5`），**图像通道默认关闭**。

原因：`stall_img_eps=0.032` 是在**压缩视频**上标定的。H.264 把静止区域量化成完全
相同的块，噪声被抹掉了；真机实时相机的传感器噪声就能让静止画面的逐像素差超过 1，
用这个阈值门控**永远不会触发**。反过来，网络卡顿时机械臂停住、编码器读数恒定，
`Δstate` 才是真机上可靠的指标。

要启用图像通道，先在你的相机上标定：

```python
from switcher import calibrate_stall
# 采两段：一段机械臂完全静止（断开控制让它停住），一段正常运动
eps_img, eps_st = calibrate_stall(still_imgs, still_states, moving_imgs, moving_states)
sw = SubtaskSwitcher(expert=2, stall_img_eps=eps_img, stall_state_eps=eps_st,
                     stall_use_image=True)
```

两个分布重叠时函数会告警 —— 那说明该通道在你的硬件上区分不了停滞，别用。

| 专家 | 整集跑完 | 切换数 | 误差中位 | ≤10帧 | ≤20帧 |

| E1 右臂抓放 | 18/18 | 36 | −2 | 69% | 94% |
| E2 左臂抓放 | 16/16 | 32 | −2 | 78% | 94% |

| 情形 | 整集跑完 | ≤10帧 | ≤20帧 |
|---|---|---|---|
| 无扰动 | **16/16** | **85%** | 93% |
| 第三视角 平移3% | 15/16 | 79% | 91% |

## 部署速度与采集速度不一致

模型**只吃当前帧**，所以速度变化不影响它认出「做到哪了」——
0.5×~2.0× 全程整集跑完率不变。但判据里有三个**步数量纲**的部件
（延迟补偿 D、连续 K 帧、EMA 平滑），会带来单调随速度的漂移：
0.5× 时约早切 7% 段长，2.0× 时约晚切 9% 段长。

同一台机器人同一套控制器，速度应当接近采集时，可以不管。
若实测差 1.5 倍以上，`tools/speed_test.py` 里有自适应 D 的实现
（把快放侧从 +9.3% 压到 +2.9%，代价是原速掉几个点）。

## 设计要点

- **只吃当前帧**：不喂帧号、不喂已执行时长、不用时序模型。
  卡顿时输入不变 → 输出不变 → 进度不推进
- **停滞门控只在信号未过线时冻结**：要防的是「卡顿期间 EMA 慢慢爬过阈值」这种
  假阳性；信号已过线的静止说明「做完了停在那儿」，该切就切
- **延迟补偿 D 按推理步计**而非墙钟时间，同样受门控冻结
- **三路视角都用**：远景第三视角给世界状态，两路腕部给夹爪附近的细节
- **判断进度主要靠画面**：消融实测只留图像几乎不掉（选点分 0.2571 vs 0.2476），
  只留 state（末端位姿/关节角）明显退化（0.3297）
